## 3. 两个实现取舍（写给以后接手的人）

1. **日志系统不存档。** 播过哪条、循环播到第几年，全部由 `sim.tick_count`（累计在线秒数）现算。
   存一份"已播列表"等于多一个能和进度失步的状态源，而代价只是"读档回退时可能重播一条"——
   一条独白重播一次，比存档结构再升一版划算。**这也意味着日志永远不会卡住进度。**
2. **显示层只做三件事：排队、计时、画字。** 淡入 0.9 秒 / 停留 8 秒 / 淡出 2.2 秒，
   一次只出一条，积压超过 3 条丢最旧的——宁可漏播，也不能排队播到天亮。

## 4. 一处值得记下的坑

第一版探针跑出来 **10 条重复**，其中 4 条是"第 88 / 260 / 400 / 480 天既在一次性表里、又在循环首年版里"——
设计侧把这三条"升格"成循环首年版时，原文说的就是"不新增、不改字"，所以它是**同一条文案的两个登记处**。
代码没有理由知道这件事，只能由数据去掉一份。

顺带发现第二个坑：避让算法把**首年**也挪了（88 → 92），因为第 88 天"和一次性条目冲突"——
可那条冲突项就是它自己。现在 `k > 0` 才避让，首年钉死。

## 6. 事件触发型（第二批）

设计侧 3.3（a）有五条草样，但**触发条件得先存在**。实装拆成两组：

| id | 触发条件 | 状态 | 文案 |
|---|---|---|---|
| `first_zijin` | `craft:zijin_dan`（第一次炼出紫金丹） | **已武装** | 炉盖掀开，他没先看丹，先看炉底。 |
| `first_jiuzhuan` | `craft:jiuzhuan_dan` | **已武装**（新增） | 九转丹出锅，他在炉边多站了一会儿。 |
| `night_no_fire` | `offline_hours:6`（离线 ≥ 6 小时） | **已武装** | 早上火还在。他拨了拨，又添了一根。 |
| `rain_flood` | 天气系统 | 未武装 | 雨下了一夜，田里积了水。他把沟又挖深一点，没把水全放干。 |
| `swallow_leave` | 燕子系统 | 未武装 | 燕子走了。窝还在，他没拆。 |
| `dog_door` | 狗系统 | 未武装 | 狗趴在门槛上。他跨过去的时候，把腿抬高了些。 |

**未武装的三条文案一个字没改**（设计侧 3.3 的定稿），等天气 / 燕子 / 狗到位时只翻 `armed`。

为了支持"第一次炼出某味丹"，`sim` 新增 `crafted`（每味丹累计出炉次数）并落盘，**`SAVE_VERSION` 升到 3**，
迁移 `_migrate_v2_to_v3` 只补一个空字典——**不臆造历史**：老存档的"第一次紫金丹"按"将来第一次"处理，
玩家可能再见一次那句话。这比编一个假次数诚实。

**事件日志的状态单独存 `user://logbook.json`**（只存"哪些事件播过"）。为什么不并进 `save.json`：
日志只是叙事，丢了顶多重播一句，不该让它的状态和游戏进度耦合、也不该为它再动存档结构。
天数类日志则完全不存——全部由累计在线秒数推导。
